## Product summary

`guard` is a lightweight LLM-powered policy checker for code, diffs, test results, logs, or arbitrary text input.

It is inspired by Python `ruff` in CLI ergonomics: fast to run, simple commands, clear reports, and useful defaults.

The CLI has two commands:

```bash
guard version
guard check
```

`guard check` reads policies from `GUARD.md`, gathers user input from git diff, files, directories, globs, file lists, or stdin, then runs an agent loop that evaluates the input against the policy items and outputs a report.

This is not an interactive coding agent. It is a non-interactive evaluator: it thinks through the policy checks, optionally calls an LLM, and prints a final report.

## Commands

### `guard version`

Print the current package version.


### `guard check`

Supported forms:

```bash
guard check --diff
guard check /path/to/dir
guard check /path/to/dir/*.py
guard check /path/to/file.py
guard check @/path/to/listoffile.txt
guard check --stdin
```

Behavior:

#### `guard check --diff`

Check only files related to the current git diff.

Use git to collect:

```bash
git diff --name-only
```

Also include staged diff if useful:

```bash
git diff --cached --name-only
```

Then read those files from disk if they exist.

Also include the actual diff content, because the LLM should reason about changed lines, not only final file content.

Use:

```bash
git diff
git diff --cached
```

#### `guard check /path/to/dir`

Recursively collect related files under the directory.

Ignore common generated or dependency directories:

```text
node_modules
.git
dist
build
coverage
.next
.turbo
.cache
venv
.venv
__pycache__
```

#### `guard check /path/to/dir/*.py`

Expand glob patterns using `fast-glob`.

#### `guard check /path/to/file.py`

Check that file.

#### `guard check @/path/to/listoffile.txt`

Read file paths from the given list file.

Rules:

* One path per line.
* Ignore blank lines.
* Ignore lines starting with `#`.
* Support relative paths based on current working directory.
* Expand globs if a listed line contains glob characters.

#### `guard check --stdin`

Read all stdin as raw input.

Important: stdin can be anything, not only code. It can be:

* test results
* linter output
* benchmark output
* logs
* generated reports
* arbitrary text

## GUARD.md

`GUARD.md` is the policy file.

Find it by walking upward from the current working directory until a `GUARD.md` is found.

Example:

```markdown
---
model: gpt-4.1-mini
provider: openai
max_iterations: 3
severity_threshold: warning
include:
  - github:inkylabs/guard-rules/javascript
  - github:inkylabs/guard-rules/security
---

# Guard Policy

## Do

- Prefer simple, readable code.
- Add early length checks before expensive array comparisons.
- Keep public APIs stable.

## Do Not

- Do not introduce unbounded retries.
- Do not log secrets.
- Do not swallow errors silently.
```

## GUARD.md includes

`GUARD.md` can include remote GitHub repos which define their own `GUARD.md` files.

Example:

```yaml
include:
  - github:inkylabs/guard-rules/javascript
  - github:inkylabs/guard-rules/security
```

* Implement local support fully.
* Implement GitHub include resolution with a simple public raw GitHub URL fetch if possible.
* If network fetch fails, produce a clear warning but continue with local rules.
* Make this easy to test by separating include resolution from CLI code.

GitHub include default behavior:

```text
https://raw.githubusercontent.com/{owner}/{repo}/{ref || "main"}/{path || "GUARD.md"}
```

## Linked files inside GUARD.md

`GUARD.md` content can reference additional local files using `@OTHERFILES.md`.

Example:

```markdown
Please also follow @SECURITY.md and @STYLE.md.
```

Behavior:

* Parse `@relative/path.md` style references from the markdown body.
* Read those files relative to the directory containing the current `GUARD.md`.
* Include their contents in the final policy context.
* Avoid infinite recursion.
* Deduplicate linked files.
* If a linked file is missing, emit a warning but continue.

## Agent loop

Implement a non-interactive agent loop.

Inputs:

```ts
type AgentInput = {
  policy: ResolvedGuardPolicy
  target: GuardTarget
  config: GuardConfig
}
```

The agent should:

1. Read the policy.
2. Read the collected target input.
3. Ask the LLM provider to evaluate whether the target violates the policy.
4. If the result is incomplete or uncertain and `max_iterations > 1`, ask a follow-up self-check.
5. Return a structured report.

For the first implementation, the faux provider should return deterministic output based on simple keyword checks so tests can pass without network calls.

Example faux behavior:

* If input contains `TODO_SECRET`, return an error finding about potential secret leakage.
* If input contains `console.log(secret`, return an error finding.
* If input contains `catch (` and an empty catch block, return a warning.
* Otherwise return pass.

Provider interface:

```ts
export interface LLMProvider {
  name: string
  evaluate(input: LLMEvaluateInput): Promise<LLMEvaluateResult>
}

export type LLMEvaluateInput = {
  systemPrompt: string
  userPrompt: string
  policyMarkdown: string
  targetContent: string
  iteration: number
}

export type LLMEvaluateResult = {
  summary: string
  findings: GuardFinding[]
  passed: boolean
}
```

## Report format

Print a clear terminal report.

Example pass:

```text
Guard Report

Status: PASS
Checked: 3 files
Policy: /repo/GUARD.md

No policy violations found.
```

Example fail:

```text
Guard Report

Status: FAIL
Checked: 2 files
Policy: /repo/GUARD.md

Findings

ERROR secret-leak src/config.ts:12
Do not log secrets.

Evidence:
console.log(secret)

Suggestion:
Remove the secret from logs or mask it.

Summary

1 error, 0 warnings, 0 info
```

Finding type:

```ts
export type GuardFinding = {
  severity: 'info' | 'warning' | 'error'
  rule?: string
  file?: string
  line?: number
  message: string
  evidence?: string
  suggestion?: string
}
```

Exit codes:

* `0`: pass
* `1`: findings at or above severity threshold
* `2`: CLI/runtime/config error

Severity threshold behavior:

* `info`: any finding fails
* `warning`: warning or error fails
* `error`: only error fails

## Important design principles

* Keep core logic independent from CLI parsing.
* Make provider system pluggable.
* Make input collection testable.
* Prefer deterministic tests.
* Do not require API keys for the initial implementation.
* Do not make the CLI interactive.
* Do not mutate user files.
* Do not auto-fix anything yet.
* Avoid huge abstractions, but keep clean boundaries.
* Output should be useful in CI.
